# Безопасное управление умным домом

## Уровни риска

| Уровень | Примеры | Разрешение |
|---|---|---|
| R0 | Чтение Git, документации, статический анализ, локальная syntax check | Можно выполнять самостоятельно |
| R1 | Локальное редактирование, unit tests, mock/preview без подключения к HA | Разрешено запросом на разработку |
| R2 | Загрузка файлов в HA, reload компонента/automation, изменение расписания, тестовая команда некритичному свету | Явное подтверждение перед деплоем |
| R3 | Вода, котёл, отопление, охрана, EV, силовые розетки, удаление интеграции, restart HA, firewall/DNS/Tailscale, ротация credentials | Отдельное подтверждение конкретного действия непосредственно перед выполнением |

Если действие относится к нескольким уровням, действует максимальный.

## Запрещённые автоматические действия

Оркестратор и агенты не должны без R3-подтверждения:

- открывать или перекрывать главный водяной кран;
- включать/выключать котёл или менять опасные температурные уставки;
- отключать защитные automation протечки, дыма или перегрева;
- ставить/снимать дом с охраны;
- запускать/останавливать EV зарядку;
- перезагружать Home Assistant или хост;
- менять сетевой доступ, TLS, Tailscale, DuckDNS или firewall;
- отзывать/создавать токены и менять пароли;
- удалять config entries, entities, backups или recorder history.

## Безопасные значения по умолчанию

- При неизвестном состоянии не отправлять противоположную toggle-команду; сначала перечитать.
- При недоступности HA не имитировать успех в UI.
- При ошибке датчика безопасности не считать дом безопасным; показывать `неизвестно`.
- При отсутствии полного массива цен не менять EV-расписание.
- При сбое внешнего API сохранять последнее подтверждённое расписание и отмечать stale data.
- При частичном деплое остановиться и либо завершить согласованный transaction, либо откатить.

## Runbook изменения Home Assistant

### До изменения

1. Зафиксировать время, цель и текущие состояния затрагиваемых entities.
2. Проверить, нет ли активной протечки, дыма, зарядки или цикла нагрева.
3. Скопировать изменяемые файлы в приватный backup с timestamp.
4. Проверить конфигурацию локально и подготовить rollback.
5. Получить подтверждение соответствующего уровня.

### Во время изменения

1. Не редактировать production-файл на месте.
2. Загружать candidate во временный файл.
3. Проверить права, синтаксис и отсутствие секретов в web-root.
4. Выполнить атомарную замену.
5. Использовать наиболее узкий reload.

### После изменения

1. Проверить HA logs и статус компонента/automation.
2. Сравнить ожидаемые и фактические entities.
3. Выполнить только заранее разрешённый canary.
4. Перепроверить состояние через 30-60 секунд.
5. При расхождении автоматически не экспериментировать: откатить или запросить решение.

## Деплой web-интерфейсов

- В `/config/www` не должно быть токенов, паролей, backup и source maps с секретами.
- Preview/mock должен быть явно отмечен и не выглядеть как production state.
- UI меняет состояние только после успешного backend-ответа.
- Для воды, охраны, EV и отопления требуется подтверждение пользователя и post-action verify.
- Новая UI-команда обязана иметь соответствующий backend allow-list и контрактный тест.

## Секреты

- Единственные допустимые источники: environment, HA `secrets.yaml` или приватный
  `local_secrets.json` с правами `0600`.
- Секреты нельзя помещать в `.claude/settings*.json`, shell allow rules, HTML, backup,
  screenshots, команды процесса или документацию.
- При обнаружении секрета не выводить его. Зафиксировать путь, тип секрета и необходимость
  ротации.
- После ротации проверить старые backups, Git history, agent logs и runtime cache.

## Откат

Откат считается готовым только если известны:

- точный backup/предыдущая версия;
- команда восстановления;
- необходимый reload/restart;
- ожидаемые состояния после восстановления;
- способ проверить физический результат.
