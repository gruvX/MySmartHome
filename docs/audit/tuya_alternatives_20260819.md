# Tuya без покупки квоты — исследование альтернатив

**Дата:** 2026-08-19 · **Режим:** READ-ONLY. Ни одна команда устройству не отправлена, ни одна
автоматизация не запущена, ни один production-файл не изменён, HA не перезапускался.
**Запрос владельца:** «я не буду покупать туя квоту она очень дорогая, ищи альтернативы».

**Главный вывод в одну строку:** покупать ничего не нужно. Исчерпанная квота относится
**только** к моему собственному IoT-Core-проекту (два скрипта), а официальная интеграция
`tuya` работает по другому, бесплатному каналу и прямо сейчас жива. Данные, которые мои
скрипты добывали из платного API, **уже лежат в памяти HA бесплатно**.

## 0. Что именно проверено, и чем это доказано

Все утверждения ниже — измерения, сделанные в этой сессии, а не рассуждения. Источники:
`/config/.storage/core.config_entries`, `core.device_registry`, `core.entity_registry`,
`/config/home-assistant.log{,.1}`, recorder БД `home-assistant_v2.db` (открыта `mode=ro`),

прослушивание UDP 6666/6667/7000 и TCP-проверка порта 6668 в LAN.

## 1. ВОПРОС 1 — квота исчерпана только у моих скриптов. Интеграция не затронута

### 1.1 Это два разных API с двумя разными системами учёта

| | официальная интеграция `tuya` | мои скрипты `tuya_leak_query.py` / `ev_query.py` |
|---|---|---|
| config entry | `01HAENTRYIDPLACEHOLDER0000`, title `ap-001165.…` | — |
| содержимое entry | `{endpoint, terminal_id, token_info, user_code}` | — |
| SDK | `tuya_sharing` (`tuya-device-sharing-sdk`) | самописная HMAC-SHA256 подпись |
| учётные данные | **user_code + QR-логин Smart Life**, client_id принадлежит Home Assistant | **TUYA_CLIENT_ID / TUYA_CLIENT_SECRET** проекта IoT Core из `/config/local_secrets.json` |
| вызываемые пути | `/v1.0/m/…`, `/v1.1/m/thing/{id}/commands` (customer API) | `/v1.0/devices?device_ids=…`, `/v1.0/devices/{id}/status` (IoT Core) |
| тарифицируется по | тарифу приложения Home Assistant | **моей Trial-подписке IoT Core** |

**Доказательство №1 — содержимое config entry.** В entry ровно четыре ключа:
`endpoint`, `terminal_id`, `token_info`, `user_code`. Ключей `access_id` / `access_secret` /
`username` / `password` там **нет**. Это в точности схема `tuya_sharing`, т.е. пути через
проект IoT Core у интеграции физически нет.

**Доказательство №2 — трассировка ошибки.** Падение 18.08 22:00 идёт через
`tuya_sharing/device.py → send_commands → POST /v1.1/m/thing/{device_id}/commands` в
`customerapi.py`. Это customer API (`/v1.1/m/…`), а не `/v1.0/devices/…`, который зовут мои
скрипты. Разные поверхности API.

**Доказательство №3 — код ошибки 28841004 в логе HA отсутствует полностью.**
`grep` по `home-assistant.log` + `.log.1`: `28841004` / `trial quota` / `quota is exhausted`
— **0 совпадений**. Этот код видит только мой скрипт-проба. Логгер `tuya_sharing` выдаёт
принципиально другие сообщения: `sign invalid` (9 раз) и `API_QPS_LIMIT_OR_DEGRADE` (3 раза).

**Доказательство №4 — прямая проба обоих путей.** С HA-бокса, «живыми» учётными данными:

```
GET /v1.0/token?grant_type=1                  success=True     ← подписка проекта ЖИВА
GET /v1.0/devices/{ev_id}                      28841004 IoT Core trial quota is exhausted
GET /v1.0/iot-03/devices/{ev_id}               28841004
GET /v2.0/cloud/thing/{ev_id}                  28841004
GET /v1.0/devices/{ev_id}/status               28841004
GET /v1.0/iot-03/devices/factory-infos?…       28841004
```

Важно: **endpoint выдачи токена по-прежнему работает.** Значит проект не отключён и подпись
верна — исчерпан именно счётчик вызовов тарифицируемых методов.

**Доказательство №5 — интеграция жива прямо сейчас, на 6-м часу «квотного» отказа.**
`mqtt_connected: True`; за последние минуты обновились `binary_sensor.motion_sensor_motion`
(438 с назад) и `sensor.smart_plug_2_voltage` (507 с). Мои же сенсоры в это время стоят на
кэше: `sensor.ev_charger_status` `src=cache`, `stale_age≈22060` с (≈6.1 ч),
`sensor.tuya_leak_cloud` `src=cache`, `cloud_age_sec≈21516`.

**Доказательство №6 — хронология разводит причины.** Отказы интеграции произошли
**раньше** квотной стены:

| время (Riga) | событие | путь |
|---|---|---|
| 18.08 22:00:00 | `API_QPS_LIMIT_OR_DEGRADE`, затем `sign invalid`; оборвана «🌙 Ночная экономия» | tuya_sharing |
| 19.08 01:58:17 | `API_QPS_LIMIT_OR_DEGRADE` | tuya_sharing |
| 19.08 ≈06:24 | начало квотной стены, скрипты уходят на кэш | IoT Core |
| 19.08 11:11 | рестарт HA | — |
| 11:11→12:54 | ошибок tuya_sharing **нет**, сущности обновляются | tuya_sharing |

### 1.2 Ответ прямым текстом

**Исчерпанная квота специфична для проекта IoT Core, которым пользуются только мои два
скрипта. Интеграцию `tuya_sharing` она не тормозит.** Следовательно: **снять зависимость
моих скриптов от IoT Core = решить этот класс отказов за 0 €.**

### 1.3 Но `sign invalid` и массовые отпадания — это ДРУГАЯ болезнь, и она не про квоту

Здесь я обязан поправить исходную формулировку задачи: «единая первопричина» — это две
независимые причины, и вторую деньги не лечат.

`API_QPS_LIMIT_OR_DEGRADE` и `sign invalid` — **серверный троттлинг customer API и порча
сессии SDK**, подтверждённый баг августа 2026 у всех пользователей:

* `home-assistant/core#179205` (2026-08-15, HA 2026.7→2026.8): ошибка возникает на
  `/v1.0/m/life/ha/access/config` (получение MQTT-конфига) → HA показывает
  «ошибку аутентификации», хотя учётные данные верны. **Лечится немедленной перезагрузкой
  config entry, без QR и без ре-авторизации.**
* `tuya/tuya-device-sharing-sdk#75` (2026-08-06, SDK 0.2.14): сессия становится
  `sign invalid` **каждые 2–3 часа**, SDK сам её не обновляет.
* `tuya/tuya-home-assistant#1070`, `core#178281`, `core#178266` — то же.
* `homebridge-tuya-ultimate#2` — та же ошибка **вне HA**, т.е. троттлинг серверный.

HA 2026.8.2 уже несёт SDK 0.2.14 (в котором Tuya пыталась это починить) — значит, доступного
апстрим-фикса нет. Гипотезу «QPS вызывает наш залп команд в 22:00» проверить не удалось: во
всех известных отчётах виноваты обновление токена и запрос MQTT-конфига, а не пакеты команд.
Совпадение с 22:00 остаётся совпадением, **не доказанной причиной**.

**Из этого следует важное:** автоматизация `1790200001001` («авто-лечение sign invalid»,
перезагрузка entry) делает ровно то, что апстрим считает единственным работающим лечением.
Она **права**, и массовые отпадания — цена этого лечения, а не отдельная поломка.

## 2. ВОПРОС 2 — локальное управление: где оно возможно, а где нет

### 2.1 Топология, которая решает всё: 23 из 38 устройств — Zigbee за шлюзом

Из диагностики интеграции (поле `sub`):

* **15 устройств `sub: false`** — прямой WiFi, локально достижимы.
* **23 устройства `sub: true`** — Zigbee-подустройства шлюза `Matter Wired Gateway`
  (`wg2`, `192.168.1.19`, протокол **3.5**).

Это критично, потому что у Zigbee-подустройств **нет собственного `local_key`**: в
customer-API-ответе ключ есть только у шлюза, и `tuya-local` трактует такие устройства как
хабы. **Локально их можно достать только через шлюз.**

И вот беда: **в категорию `sub: true` попало всё, что отвечает за безопасность** — все
4 датчика протечки, кран воды, сирена, дверь, оба PIR и Гидрофор. А в `sub: false` —
как раз вся энергетика, которой рулит Nord Pool.

### 2.3 Проверка утверждения «proto 3.5 → LocalTuya не поддерживает»

**Утверждение устарело и неверно** для обоих живых проектов:

* `xZetsubou/hass-localtuya`: 3.5 с сентября 2023 (PR #15, PR #26 → релиз 3.1.0);
  `SUPPORTED_PROTOCOL_VERSIONS = ["3.3","3.1","3.2","3.4","3.5"]` — в том числе **в
  установленном здесь теге `2025.11.0`**. В 2026.7.0 отдельно правили «v3.5 session key
  negotiation failures on reconnect» (#809).
* `make-all/tuya-local`: 3.1/3.2/3.3/3.4/3.5 + виртуальные 3.42/3.52 (2026.8.0).
* Верно оно только для **оригинального** `rospogrigio/localtuya`: его README до сих пор
  говорит «from 3.1 to 3.4», 3.5 нет.

Источник путаницы — статьи 2025 года про оригинальный localtuya. Заметку в проекте
(«EV charger: proto 3.5 — LocalTuya doesn't support it») **надо исправить**.

| поддержка | активная (7 релизов за 3 мес.) | активная | фактически заброшен (1575 открытых issue) |

| протоколы | 3.1–3.5, 3.22, 3.42, 3.52 | 3.1–3.5 | 3.1–3.4 (**нет 3.5**) |

| получение `local_key` | **QR-логин Smart Life, без IoT-проекта** | «Cloud API» шаг — **требует живой IoT Core** (код 28841002/28841004 обрабатывается в коде) → **здесь не сработает** | требует IoT-проект |
| Python 3.14 (дефолт с HA 2026.3) | в зоне поддержки | 2025.11.0 **старше** этого рантайма; отчётов о поломке нет, но и подтверждения нет | — |

**Первопартийного локального пути нет:** core-интеграция `tuya` — исключительно облачная.

**Сосуществование с облачной интеграцией.** Обе могут работать одновременно: домены разные
(`tuya` и `tuya_local`), unique_id разные, поэтому **entity_id не столкнутся** — у локальной
копии появятся свои сущности (обычно с суффиксом `_2` или своим именем). Это значит:
история и long-term statistics **не переносятся** — новая локальная сущность начинает
статистику с нуля, а старая замирает. Чтобы сохранить историю и не переписывать 72
автоматизации, правильный путь — после проверки локальной сущности **отключить облачную и
переименовать локальную в освободившийся entity_id** (тогда recorder продолжит ту же серию).
Двойное управление одним реле из двух интеграций одновременно оставлять не стоит: состояния
будут расходиться.

### 2.5 Как получить `local_key` без платной квоты

| способ | статус на 2026-08 |
|---|---|
| **IoT Core `/v1.0/devices/{id}`** (там лежит `local_key`) | ❌ **проверено здесь: 28841004.** Пока квота исчерпана — недоступно |
| **`tuya-cli wizard` (tuyapi)** | ❌ тоже требует IoT-проект → та же квота |
| **customer API `tuya_sharing`** (`/v1.0/m/life/ha/home/devices`) | ✅ **рабочий бесплатный путь.** `CustomerDevice` несёт поле `local_key`; доступ по user_code + QR-логин Smart Life, **без IoT-проекта, без Access ID/Secret**. Встроено в `tuya-local` (`cloud.py`); есть и отдельный инструмент `vineetchoudhary/tuya-local-key` (v1.6/1.7, 08.2026) |
| **хранилище самой интеграции HA** | ❌ `local_key` живёт только в ОЗУ (`manager.device_map[id].local_key`), в config entry его нет, и **в diagnostics он намеренно вырезан** (17 полей, `local_key` среди них отсутствует) — проверено: в 370 КБ дампа ключей нет |
| **дамп/MITM приложения Smart Life** | ⚠️ работает, но нужен root/эмулятор; `tinytuya`-визард сюда **не относится** (он тоже про IoT Core) |
| **`tuya-convert` / `tuya-cloudcutter`** | ❌/⚠️ `tuya-convert` мёртв (только ESP8266). `cloudcutter` не берёт пропатченные прошивки после 2021 → нужен провод, и устройство навсегда уходит из Tuya-приложения |

**Ответ:** да, `local_key` берётся бесплатно — через QR-логин Smart Life
(`tuya-local` умеет это сам). Но **только для 15 прямых WiFi-устройств**: у 23
Zigbee-подустройств ключа не существует в принципе.

⚠️ **Не проверено и важно:** делит ли `tuya-local` QR-логин один `TUYA_CLIENT_ID` с
официальной интеграцией и **не «отстрелит» ли он её сессию** (`terminal_id` разные, но
подтверждений в обе стороны найти не удалось). На фоне уже идущей войны с `sign invalid`
это надо проверять осознанно, а не считать безопасным.

### 2.7 Итог по вопросу 2

Локализация **разрубает дом надвое**: энергетику (то, что экономит деньги) перевести
локально можно и, вероятно, стоит; безопасность (протечка, кран, сирена) локально
недостижима без работы через шлюз, которая не подтверждена, или без замены радиоканала.

**Ещё один бесплатный путь, который дают сами данные дома:** уже настроенная и живая
интеграция **SmartThings** дублирует 16 физических Tuya-устройств — включая

свет. Это **независимый от Tuya облачный канал управления, уже работающий, 0 € и 0
установок**. Чего в нём нет: **датчиков протечки** (проверено — SmartThings отдаёт только
`Кухня` t/h и дверную сигнализацию, оба `_2`).

## 3. ВОПРОС 3 — что делать с моими двумя скриптами

### 3.1 Ключевой факт: их данные уже есть в HA бесплатно

Через локальный `/api/diagnostics/config_entry/01HAENTRYIDPLACEHOLDER0000` (370 КБ, **0.04 с**,

Душевая (sj): {"watersensor_state": "2", "battery_percentage": 100}

`forward_energy_total = 104023` при `scale 2` = **1040.23 kWh** — ровно то, что показывает
`sensor.ev_charger_energy`. `work_state = charger_insert` — ровно то, что показывает
`sensor.ev_charger_status`. **Мой платный запрос дублировал то, что уже пришло по MQTT
бесплатно.** Более того, сейчас версия из памяти **свежая**, а моя — кэш 6-часовой давности.

Почему сущностей нет: core-интеграция для категории `qccdz` создаёт только
`switch.ev_charger_switch`. Ни `work_state`, ни `forward_energy_total` не замаплены — даже
как `disabled` (проверено в `core.entity_registry`: у устройства EV Charger **ровно одна**
сущность). Так что «включить отключённую сущность» — не вариант.

### 3.2 Арифметика бесплатного тарифа — почему «просто реже опрашивать» не спасает

Trial Edition IoT Core = **26 000 вызовов API + 68 000 сообщений в месяц**, счётчик
обновляется в начале месяца. Мои endpoint'ы (`/v1.0/devices?device_ids=`, 1 вызов на 4
датчика; `/v1.0/devices/{id}/status`, 1 вызов):

| режим | вызовов/сутки | вызовов/месяц | доля 26 000 |
|---|---|---|---|
| протечка @30 с (как было) | 2 880 | ~86 400 | **332 %** → квота выгорает за ~9 суток |
| протечка @180 с (развёрнуто сегодня) | 480 | ~14 400 | 55 % |
| EV @300 с (общий кэш 290 с) | ~288 | ~8 640 | 33 % |
| обновление токена | ~24 | ~720 | 3 % |
| **итого после сегодняшнего снижения** | **~792** | **~23 760** | **~91 %** |
| + форсаж «датчики слепы» (худший случай по комментарию автоматизации: 48 эпизодов × 20) | до 1 440 | до 43 200 | **166 %** |

Отсюда два вывода:
1. Режим 30 с объясняет выгорание: ~9 суток от полного бака — и первые отпадания Tuya
   действительно начались 16.08.
2. **Снижения до 180 с недостаточно.** В покое это 91 % месячной квоты, а при срабатывании
   форсажа — гарантированный перерасход. Уменьшать интервал недостаточно; надо **убрать**
   зависимость от IoT Core.

⚠️ **Не проверено:** что счётчик действительно обнулится 01.09. Документация Tuya говорит о
месячном пакете и «возобновлении в следующем месяце», но подтвердить это в этом доме можно
только наблюдением. Проверка бесплатна: повторить пробу `GET /v1.0/devices/{id}` 1 сентября.
Также не удалось выяснить, тарифицируется ли сам `/v1.0/token` (сейчас он отвечает `success`).

### 3.3 `sensor.ev_charger_status` / `_energy` — рекомендация: убрать IoT Core, взять из памяти HA

Самая дешёвая правильная замена. Два варианта, оба 0 €:

* **(рекомендуется) маленький custom-компонент**, который берёт уже существующий объект
  менеджера интеграции и публикует незамапленные DP (`work_state`, `forward_energy_total`,
  `work_mode`, `charge_energy_once`) как сенсоры. Ноль облачных вызовов, обновление
  push'ем по MQTT, работает и без интернета к IoT Core. ~100–150 строк.
* **(быстрее, грязнее) переписать `ev_query.py`** так, чтобы он читал не Tuya, а локальный
  `/api/diagnostics/config_entry/...` на `127.0.0.1`. Сохраняются entity_id, атрибуты
  `src`/`stale_age`, все автоматизации и тесты. Минус: diagnostics — не стабильный
  контракт, формат может измениться с версией HA.

Что теряем: ничего. Данные те же, свежее и без квоты. Долгосрочно правильнее всего — PR в
HA core на маппинг категории `qccdz` (тогда сенсоры станут первопартийными).

### 3.4 `sensor.tuya_leak_cloud` — здесь есть настоящая потеря, и её надо назвать

Смысл этого сенсора — **независимость**: интеграция умеет «замирать» (состояния не
меняются, `unavailable` не появляется, сторож не видит отказа) — это описано в самой
автоматизации `1790200001001` и подтверждается баг-репортом SDK #75 («сессия дохнет каждые
2–3 часа»). Облачный бэкап ловил именно такой отказ.

| вариант | цена | независимость | вердикт |
|---|---|---|---|
| **A. Убрать, довериться интеграции** | 0 € | ❌ утрачена | Приемлемо только вместе с детектором «замирания» (ниже). `sensor.leak_protection_status` — единственный источник истины, его логику ломать нельзя (`tests/test_leak_truth.py`) |

Детектор замирания (0 €, ничего не устанавливать): у нас есть два независимых от

### 4.3 Базовая линия «ничего не делать»

При сохранении сегодняшней конфигурации (протечка 180 с, EV 900/300 с):

* **До конца августа:** `sensor.tuya_leak_cloud` и оба EV-сенсора продолжают отдавать кэш;
  `stale_age` растёт (уже ≈6.1 ч). Основной путь защиты от протечки
  (`binary_sensor.*_moisture` + 3-секундное подтверждение в v4) **работает** — квота его не
  касается. То есть дом защищён, но **резервного пути нет, и это не видно нигде, кроме
  атрибута**.
* **EV:** `sensor.ev_charger_energy` замер → суточный и месячный учёт киловатт-часов и
  вечерний отчёт занижают EV; `sensor.ev_charger_status` как резервный триггер интерлока

* **Независимо от квоты:** `sign invalid` продолжает рвать автоматизации в момент отправки

перезапускался, production-файлы не изменялись. Секреты и pairing-коды не выводились.

**Источники этого раздела (всё измерено сегодня):** `/config/.storage/core.device_registry`,
`core.entity_registry`, `core.config_entries`; `/api/diagnostics/config_entry/<matter>`,
`<thread>`, `<tuya>`; Supervisor API `GET /addons`, `/addons/core_matter_server/info`,
`/addons/core_matter_server/logs`; recorder БД (`mode=ro`); пассивный + активный mDNS-опрос
(`_matter._tcp`, `_matterc._udp`, `_meshcop._udp`, `_trel._udp`) с HA-бокса; ARP-таблица;
исходники интеграции `matter` тега HA 2026.8.2 на GitHub.

## 6.0 Ответ владельцу в пяти строках

1. **Шлюз действительно умеет быть Matter-мостом — это не теория.** Он уже был мостом в этом
   доме: 15–18 декабря 2025 HA получил через Matter 5 устройств / 19 сущностей, и 4 из 5 —
   это его **Zigbee-подустройства** (PIR, 4-кнопочный пульт, два диммера). Доказательство —
   древо `via_device` в реестре и Matter-эндпоинты в unique_id.
2. **Но мост умер 18.12.2025 и сам не оживёт: HA потерял свою Matter-фабрику.** Шлюз до сих
   пор объявляет в LAN старую фабрику HA, а Matter-сервер HA сейчас работает в **другой**
   фабрике с **нулём узлов**. Отсюда `unavailable` у всех 15 живых сущностей.
3. **Ни один критичный прибор через мост никогда не проходил** — и не мог: сирена, кран и все
   4 датчика протечки были подключены к Zigbee-шлюзу **позже** (март–апрель 2026), уже после
   смерти моста. Мост не «отказался» их отдавать — его тогда уже не было.
4. **И самое важное — ответ на сам вопрос: нет, для защиты дома шлюз проблему не решает.**
   Мост отдаёт наружу не «все свои Zigbee-устройства», а **жёсткий список, зашитый в
   прошивку** (§6.2): непопавшее устройство физически отсутствует в его
   Descriptor/PartsList, и его не увидит **никакой** Matter-контроллер — ни HA, ни Apple,
   ни Google. По документальным признакам (§6.2.2) прошивка этого шлюза сертифицирована по
   **Matter 1.0**, а типы «датчик протечки» и «водяной клапан» появились только в
   **Matter 1.2** — то есть их там, скорее всего, просто нет как понятия. Сирены в Matter
   нет вообще ни в одной версии. Плюс §6.2.3: у таких мостов документированная привычка
   терять и заново создавать bridged-устройства (новые entity_id) — для защиты от протечки
   это дисквалифицирующе само по себе.
5. Итог: **Matter-мост — бесплатный и полезный путь для света/выключателей/PIR/пультов
   (это ~11 из 23 облачных устройств), но НЕ для протечки, крана и сирены.** Проверка §6.6
   всё равно стоит 0 € и 5 минут — она подтвердит или опровергнет вывод фактом, а не
   документами. Zigbee-стик остаётся единственным путём для защиты дома.

### 6.1.1 Это и есть шлюз — вместе с его Zigbee-детьми

Реестр устройств HA (`core.device_registry`), config entry `matter`
`01HAENTRYIDPLACEHOLDER0000`, все 5 созданы **2025-12-15 14:10 UTC** в одну секунду:

|---|---|---|---|---|
| **Gateway** | `deviceid_<matter-node-id>-MatterNodeDevice`, serial `<gateway-serial>` | **MIUC Technology** | Gateway, model_id **2373**, hw 1.0, **sw 2.0.0** | — (корень) |

(«2DimmerSwitch»), а не пользовательские Tuya-имена («Второй этаж»).

это отпечаток корневого сертификата фабрики на момент сопряжения. `<matter-node> ≠

## 6.2 Мостит ли шлюз Zigbee-детей — и какие именно классы

**Мостит: доказано** (§6.1.1) — для PIR, беспроводного 4-кнопочного пульта и диммеров света.

**Дозапись после веб-разысканий (см. пометки о достоверности): по датчикам протечки, крану и
сирене ответ, скорее всего, ОТРИЦАТЕЛЬНЫЙ.** Ниже — механизм, из-за которого это так, и
граница между измеренным здесь и вычитанным в сети. Ни одно утверждение из интернета не
считается здесь фактом наравне с измерением.

### 6.2.1 Механизм: мост отдаёт не «выборку владельца», а зашитый в прошивку список

Разработчик Zigbee-квирков kkossev на форуме самой Tuya проследил, почему часть
подустройств не появляется у контроллера, до уровня протокола:

> «TS0601 `_TZE200_cf1sl3tj` Curtain Motor … is supported. `_TZE200_68nvbio9` is supported as
> well. However, TS0601 `_TZE200_xuzcvlku` (also sold by Zemismart) **is not exposed by Tuya
> GW (not in the BridgeDescriptor 0x001D PartsList attribute 0x0003)**»
> — tuyaos.com/viewtopic.php?t=2863, 2024-03-05. **Достоверность: высокая (уровень протокола,
> но это форум, не спека).**

Это ровно то, что я измерил здесь независимо: в декабре 2025 на шлюзе было **13**
Zigbee-детей, а bridged-эндпоинтов он объявил **4**. Причём отбор идёт не по «классам
устройств вообще», а по конкретным моделям — у kkossev не проходят даже разные прошивки
одного и того же TS0601. Отсюда важное следствие: **не появившееся в PartsList устройство
невидимо для любого контроллера** — ни для HA, ни для Apple, ни для Google. Это не проблема
интеграции и не лечится настройками.

Владелец, скорее всего, вообще не выбирал галочками — версия «мост отдал что разрешает
прошивка» теперь сильнее версии «владелец отметил 4 устройства». Различить их read-only
по-прежнему нельзя, но §6.6 различит.

**Сторона HA точно не виновата** — подтверждает кодовладелец интеграции `matter`
(marcelveldt), разбирая чужой диагностический дамп:

> «HA has support for all these device types so if they don't show up, its most likely because
> they are simply not yet bridged to Matter by the … bridge» / «I just inspected your
> diagnostics dump and I can confirm that these device types are not exposed by the Ikea
> bridge»
> — home-assistant/core#142789, 2025-04-28. **Достоверность: высокая (кодовладелец), но речь
> о мосте IKEA, не Tuya.**

Это согласуется с моим прямым чтением исходников HA 2026.8.2 (**измерено**):
`matter/binary_sensor.py` содержит `device_types.WaterLeakDetector` +
`clusters.BooleanState.Attributes.StateValue`, а также `WaterFreezeDetector`, `RainSensor`,
`ContactSensor`; `matter/valve.py` содержит `WaterValve` + `ValveConfigurationAndControl` с
open/close и позицией. Значит, **если** мост их объявит — HA создаст сущности сам, без
кастомного кода. Узкое место — исключительно прошивка моста.

### 6.2.2 Потолок версии Matter: почему протечки и крана там, вероятно, нет как понятия

| признак | значение | достоверность |
|---|---|---|
| что шлюз сообщает о себе в Matter (**измерено здесь**) | vendorName `MIUC Technology`, productName `Gateway`, productID **2373** (0x0945), hw 1.0, **sw 2.0.0** | измерено |
| сертифицированный «родственник» в базе CSA | «The Matter Wired Gateway» **by MOES**, VID 0x147D / PID 0x0638, сертификат CSA23J45MAT42448-00 от 2023-11-28, **FW 2.0.0, HW V1.0.4, Matter Spec 1.0**, Ethernet, device type 0x000E (Aggregator) | веб, средне-высокая. **PID не совпадает** (0x0638 ≠ 0x0945) ⇒ это одна референс-платформа под разными марками, а **не** та же самая запись сертификата |
| список кластеров в DCL для productID нашего шлюза | Boolean State, Occupancy Sensing, **Thermostat**, On/Off, Level Control, Color Control, Window Covering, Access Control, Groups, Labels — **нет `ValveConfigurationAndControl`**, нет `SmokeCoAlarm` | веб, средняя (часть страницы за пейволом) |

Из этого складывается главный аргумент, и он документальный, а не измеренный:

* Типы устройств **WaterLeakDetector (0x0043), WaterFreezeDetector, RainSensor и WaterValve
  появились в Matter 1.2** (осень 2023). Прошивка, сертифицированная по **Matter 1.0**, таких
  типов не знает — их нечем объявить.
* В DCL-списке кластеров для этого productID **нет** `ValveConfigurationAndControl` ⇒ кран
  как `valve` не приедет.
* `Boolean State` в списке **есть**, но в эпоху 1.0 он обслуживает `ContactSensor` (дверной
  датчик), а не датчик протечки. Присутствие кластера **не** равно присутствию типа
  устройства.
* `Thermostat` в списке есть, хотя в публичной табличке Tuya его нет ⇒ **табличка Tuya — это
  минимум, а не контракт**; список надо читать по конкретному прибору, а не по маркетингу.

**Оговорка, которую нельзя опускать:** совпадают строка прошивки (2.0.0) и класс устройства,
но productID у нашего шлюза другой, а прошивку с декабря 2025 могли обновлять. Поэтому
«Matter 1.0» — это **сильное документальное указание, а не измеренный факт**. Прочитать
`ClusterRevision`/список типов с самого прибора можно только внутри его фабрики, т.е. после
сопряжения (§6.3, шаг 5) — либо бесплатно в чужом приложении (§6.6).

### 6.2.3 Отдельный, самостоятельно дисквалифицирующий риск: мосты теряют эндпоинты

Даже если бы протечка приезжала, этот транспорт **нельзя** ставить под защиту дома. У
Tuya-мостов документированная привычка терять bridged-устройства и добавлять их обратно
**как новые**, с новыми идентификаторами, именами и комнатами:

> «When the bridge loses power all the connected devices in SmartThings disappear from
> SmartThings breaking my automations» — tuyaos.com t=3404, 2024-06-28 (у того пользователя
> вылечилось прошивкой шлюза 1.10.505). Плюс: исчезновение раз в несколько дней с возвратом
> под именами по умолчанию (t=3330, 2024-06-10); новые подустройства не доезжают, пока не
> перезагрузить **оба** хаба; и регресс на стороне HA — bridged-эндпоинты перестали
> становиться сущностями в 2025.2+, хотя видны в веб-интерфейсе Matter Server
> (home-assistant/core#142850, закрыт как stale). **Достоверность: пользовательские отчёты.**

Для этого дома это означало бы: `binary_sensor.*_moisture` в 20 автоматизациях и в
`sensor.leak_protection_status` в любой момент превращаются в новые entity_id, а старые —
в `unavailable`. То есть защита от протечки ломается **тихо**. Отдельно отмечу: это
**возможное** (не доказанное) объяснение и того, почему мост здесь прожил всего 2.5 суток в
декабре 2025 — но мои измерения указывают на потерю фабрики на стороне HA, так что
причинно-следственная связь не установлена.

### 6.2.4 Сирена — невозможна, и это структурно

В спецификации Matter (включая 1.5.1) **нет типа устройства «сирена»**. В HA
`matter/siren.py` реализован ровно один случай — **вендорский кастомный кластер Heiman**
(`HeimanCluster.Attributes.SirenActive`) — **измерено в исходниках**. Ни одного отчёта о
проброшенной через Tuya-мост сирене веб-разыскания не нашли (ни успешного, ни жалобы).
Tuya-сирена (`sgbj`) в лучшем случае приедет как обычный on/off, без режимов и мелодий.

| дверной/контактный датчик | вероятно да | `Boolean State` + `ContactSensor` есть уже в 1.0 |
| термостаты / тёплый пол (Zigbee) | вероятно да | `Thermostat` в DCL-списке (веб, средняя) |
| T&H-датчик «Кухня» | **нет** (не приехал) | измерено здесь: 4 из 13 |
| **датчики протечки** | **скорее всего нет** | тип из Matter 1.2, прошивка по признакам 1.0 (веб, средне-высокая) |
| **кран воды** | **скорее всего нет** | нет `ValveConfigurationAndControl` в DCL (веб, средняя) + тип из 1.2 |
| **сирена** | **нет** | в Matter нет такого типа (структурно) |

«Мост отдаёт всё» — **опровергнуто измерением**. «Мост отдаёт защиту дома» — **не
подтверждено и по документам маловероятно**. Прежняя формулировка этого раздела
(«протечка и кран — вероятно да») **отменяется**: она опиралась на готовность HA, а узкое
место оказалось в прошивке моста.

## 6.3 Если мост всё-таки возвращать (для света/выключателей) — что именно нужно

**Важно:** после §6.2 этот раздел перестал быть путём к защите дома. Он остаётся актуальным
для света/выключателей/PIR/пультов — а это ~11 из 23 облачных устройств, которые перестанут
зависеть от `sign invalid`. Порядок — от безопасного к необратимому. **Шаги 3+ — это изменение дома, только по решению
владельца.** Ничего из этого мною не выполнялось.

0. **Ничего не покупать и ничего не устанавливать** — add-on Matter Server 9.2.0 уже стоит,
   запущен, `boot=auto`, обновлений нет; интеграция `matter` уже настроена. Bluetooth в
   сервере выключен, но он и не нужен: шлюз проводной, сопряжение пойдёт «on-network» по IP.
1. **Бесплатная проверка без изменений (см. §6.6)** — посмотреть в том стороннем приложении,
   которое уже сидит в одной из двух живых фабрик шлюза, какие устройства оно оттуда получило.
   Это и есть эмпирическая проверка вывода §6.2: если протечка и кран там **видны** — мой
   документальный вывод неверен, и Zigbee-стик не нужен; если не видны — вывод подтверждён
   фактом.
2. **Почистить мёртвую фабрику HA на шлюзе.** Слот `<matter-node>` занят навсегда:
   удалить его может только контроллер этой фабрики (его больше нет) либо приложение Tuya
   («убрать из экосистемы …»). Спека гарантирует минимум 5 фабрик; сейчас занято 3 из
   неизвестного лимита, после добавления HA станет 4. Если приложение позволяет отвязать
   старую — сделать это **до** нового сопряжения. Заводской сброс шлюза (`factory_reset`
   есть в его Tuya-DP!) для этого использовать **нельзя** — он снесёт всю Zigbee-сеть из 23
   устройств. Этот DP вообще не должен трогаться никогда.
3. **Взять новый pairing-код** — **исправлено по документации Tuya** (в первой редакции этого
   раздела путь был указан неверно): открыть в приложении Smart Life/Tuya **карточку самого
   шлюза** → **⋯ (три точки) в правом верхнем углу** → **«Share via Matter Gateway»**
   («Поделиться через Matter-шлюз»). Пути «Me → Home Management» здесь нет: «Me → шестерёнка»
   — это выдача Tuya **User Code** для облака, совсем другая вещь.
   > «open the hub connected to the Zigbee device on the Tuya-enabled app, tap the meatballs
   > menu (⋯) in the top right corner, and select **Share via Matter Gateway** to generate a
   > code» — developer.tuya.com, «Interoperability of Matter Products». **Достоверность:
   > документация вендора.**

   Код **одноразовый и с ограниченным сроком**: «The sharing code is one-time-use and
   time-limited… **Once the sharing is complete, the sharing code becomes invalid**». Код
   нигде не записывать и не пересылать. В этот момент шлюз начнёт объявлять `_matterc._udp` —
   сейчас он его **не** объявляет (проверено), т.е. окно сопряжения закрыто и случайно никто
   не подключится.

   **Структурный факт из тех же документов, который закрывает вопрос «не потеряем ли Tuya»:**
   > «Bridged Zigbee devices are not Matter-enabled products, so they do not have a pairing
   > code and therefore cannot generate a sharing code. However, you can generate a sharing
   > code of the bridge hub» / «Tuya-enabled Zigbee devices **cannot** be directly added to
   > third-party Matter-enabled apps».

   То есть приложение Tuya — **единственное** место, где живут сами Zigbee-подустройства, и
   HA никогда не станет их единственным администратором. Это не недостаток конкретно этого
   шлюза, это конструкция.
4. **HA → Настройки → Устройства → Matter → «Добавить устройство»** → ввести код. Сопряжение
   локальное, через LAN. Multi-admin у шлюза измерен (3 фабрики) ⇒ **связь с приложением Tuya
   не теряется**, старые 23 облачные сущности продолжают работать как сейчас.
5. **Смотреть, что приехало.** Это и есть настоящий ответ на §6.2. Ожидать: новые устройства
   с generic-именами («WATER SENSOR», «Zigbee Smart Valve»), новые unique_id с префиксом
   `E77DA06773F78DB7-…`, новые entity_id с суффиксами.
6. **Только если приехало нужное — переезд без переписывания автоматизаций.** Он в этом доме
   обязателен аккуратный: критичные entity_id упомянуты в **20 автоматизациях** (из 72), в
   `configuration.yaml` (template-сенсоры, включая `sensor.leak_protection_status` — единый
   источник истины по протечке), в `scripts.yaml`, в планшете и Mini App. Счётчик ссылок:
   `siren.alarm` — 38, `voda_kran_switch_1` — 33, `vannaia_moisture` — 23,
   `garazh_moisture` — 23, `water_sensor_4_moisture` — 22, `kukhnia_moisture` — 21,
   `zigbee_plug_2_socket_1` — 16. Правильный порядок: **сначала** сутки наблюдать новую
   Matter-сущность рядом со старой, **потом** отключить облачную и **переименовать**
   Matter-сущность в освободившийся entity_id — тогда история и long-term statistics
   продолжатся в той же серии, а ни одна автоматизация не правится. Двойное управление одним
   краном из двух интеграций одновременно не оставлять.
7. **Удалить 19 сущностей-призраков** старой фабрики (`F7B5…`) — они не вернутся никогда и
   только шумят в «недоступных». Один призрак уже попал в автоматизацию:
   `sensor.occupancysensor_batareia` под меткой «Занятость» стоит в списке батарей
   🧠 Самодиагностики дома v3 (id `1765960140022`). Вреда нет — шаблон делает
   `float(-1)`, а фильтр `0 <= v < 20` минус единицу не пропускает, поэтому ложных
   «0 %»-алертов не было и нет; но при чистке призраков эту строку надо убрать вместе с ними.

**Риски шага 4, честно:** (а) неизвестно, сколько фабрик держит прошивка шлюза — публичного
значения `SupportedFabrics`/`CommissionedFabrics` ни для одного Tuya/MOES/AVATTO/Zemismart
шлюза найти не удалось, «5» — это **минимум по спеке**, а не измерение; занято 3 (одна
мертва), и, по веб-данным, одна только Apple Home съедает **два** слота, так что упереться в
лимит реально. Если лимит исчерпан — сопряжение просто не начнётся (это отказ, а не поломка);
(б) неизвестно, влияет ли работа в 4 фабриках на стабильность Zigbee-сети шлюза;
(в) в декабре 2025 мост прожил всего 2.5 суток — возможно, это и есть §6.2.3 (потеря
эндпоинтов), но мои измерения указывают на потерю фабрики на стороне HA; причина не
установлена; (г) обновление прошивки шлюза может как починить bridging, так и снести фабрики;
(д) **главное «нельзя»: не сбрасывать шлюз аппаратной кнопкой.** «You mustn't reset the
accessory back to pairing mode from the hardware button, or you'll break the original
connection» (TP-Link FAQ 3573) — аппаратный сброс, как и Tuya-DP `factory_reset`, рвёт и
Zigbee-сеть, и все фабрики; (е) §6.2.3 в силе и здесь: даже для света bridged-устройства
могут исчезнуть и вернуться новыми entity_id — поэтому в переезд (шаг 6) для света идти
только после **недели** наблюдения, а не суток.

## 6.4 Чем шлюз ценен независимо от моста (это HA сейчас не использует)

* У шлюза есть собственный **тревожный канал**: writable DP `master_state` (`normal|alarm`),
  `switch_alarm_sound`, `alarm_active`. HA из всего этого показывает **только**
  `binary_sensor.matter_wired_gateway_problem`. То есть в доме есть **вторая сирена/ревун**,
  про которую ни одна автоматизация не знает — а сирена №1 (`siren.alarm`) стоит на том же
  облачном пути, что и всё остальное, и уже имеет отдельный сторож «сирена недоступна».
* Шлюз — **Thread Border Router** (`_meshcop._udp`: `vn=OpenThread`, `nn=TMSthread_e502`,
  `tv=1.3.0`; плюс `_trel._udp`). Второй border router в доме — хаб SmartThings на
  `192.168.1.35` (`nn=ST-TIZEN`, `tv=1.4.0`). Значит **Thread-устройства (не Zigbee) можно
  вводить в HA локально уже сейчас**, без покупок.
* `support_local: true`, протокол 3.5, TCP 6668 открыт — шлюз доступен и по локальному
  Tuya-протоколу, если когда-нибудь появится `local_key`.

* **Формулировка §2.1 «локально их можно достать только через шлюз» верна и сейчас** —
  Matter-мост это как раз «через шлюз», просто второй способ, который я в первой редакции не
  рассмотрел вовсе. Это была моя недоработка.

**Важно про перепаривание в любом варианте:** и Zigbee-стик, и Matter-мост дают устройствам
**новые** entity_id. Стик дополнительно требует физически перепаривать 23 устройства (кнопки
на датчиках, доступ к шлюзам света в подрозетниках). Matter-мост не требует ничего физически.

## 6.6 Проверка за 0 €, 0 риска, 5 минут — её может сделать только владелец

Шлюз **прямо сейчас** состоит в двух живых сторонних Matter-фабриках
(`1AF4835B49A9FE0A`, `C1BCA1B83D8ECEC1`) — то есть какое-то приложение (Apple Home / Google
Home / Alexa / SmartThings — определить по mDNS невозможно) уже получает от него
bridged-устройства. Достаточно открыть это приложение и посмотреть список устройств от
«SmartGateway / Matter Wired Gateway»:

* **видны датчики протечки и кран воды** ⇒ мой документальный вывод §6.2 **неверен**, мост
  отдаёт защиту дома ⇒ §6.3 шаги 2–7, стик не нужен, всё бесплатно (но §6.2.3 всё равно
  требует недели наблюдения перед переносом автоматизаций);
* **видны только света/выключатели/PIR/пульты** ⇒ вывод §6.2 подтверждён фактом ⇒

* **приложение вообще не помнит этот шлюз** ⇒ фабрики такие же мёртвые, как у HA, и
  единственный способ узнать — шаги 3–5 из §6.3 (сопряжение), это уже решение владельца.

Второй бесплатный источник ответа — приложение Tuya: карточка шлюза → **⋯ → «Share via Matter
Gateway»**; экран показывает список того, что будет расшарено, **до** генерации кода. Дойти до
этого экрана и **не** нажимать «сгенерировать» — уже безопасно и уже отвечает на вопрос.

## 6.7 Что в этом разделе не проверено (и почему)

1. **Отдаёт ли мост датчики протечки / кран / сирену — не ИЗМЕРЕНО.** Read-only измерения
   нет: Matter не позволяет читать эндпоинты узла без операционных ключей фабрики (анонимного
   чтения в протоколе нет), а сопряжение = изменение дома. Вывод §6.2 («скорее всего нет»)
   опирается на веб-источники средней и средне-высокой достоверности, не на прибор.
   Единственные бесплатные способы проверить — §6.6.
2. **Почему умерла фабрика 18.12.2025.** Данных не осталось: логи HA хранят ~15 ч, логи
   add-on'а — с последнего старта (18.08), recorder — 12 суток, все 3 бэкапа (17–19.08) уже
   после потери. Переустановка add-on'а, потеря `/data` и восстановление из старого бэкапа
   дают одинаковый след.
3. **Кому принадлежат две живые фабрики шлюза.** mDNS раскрывает только compressed fabric ID
   и node ID; вендора контроллера — нет. `1AF4835B49A9FE0A-0000000100000000` и
   `C1BCA1B83D8ECEC1-0000000017D475E6`. Определяется только владельцем (§6.6).
   **Кандидаты по 45-секундному перечислению сервисов в LAN (это догадка, не факт):**
   Apple TV `192.168.1.24` («Главная спальня», `_airplay` + `_companion-link` +
   `_sleep-proxy` — типичный домашний хаб Apple Home); хаб SmartThings в телевизоре
   Samsung `192.168.1.35` (`_smartthings._tcp` = `D052A8E4B86E0001`, и он сам —
   Matter-узел `F97C668AA6847640-B5E92C99649FAA95`, т.е. состоит в чьей-то фабрике);
   Google Home через Chromecast-приёмник `Q80F…` на том же `.35`. Фабрика Tuya в этот
   список не входит: приложение Tuya управляет своими Zigbee-детьми нативно, а не по Matter.
   Ни одно устройство в сети **не** объявляет `_matterc._udp` ⇒ ни один прибор сейчас не
   открыт для сопряжения, случайно подключиться некому.
4. **Кто такая «MIUC Technology» и что за productID 2373 (0x0945).** Это то, что шлюз сам
   сообщает в Matter BasicInformation; в Tuya тот же прибор называется `Matter Wired Gateway`,
   `wg2`, `jdoybmqvqvdoyle1`. В базе CSA найден **сертифицированный «родственник»** — «The
   Matter Wired Gateway» **by MOES**, VID 0x147D / PID 0x0638, CSA23J45MAT42448-00
   (2023-11-28), FW 2.0.0 / HW V1.0.4 / **Matter Spec 1.0** / Ethernet / device type 0x000E.
   **Но PID не совпадает** (0x0638 ≠ 0x0945) ⇒ это одна референс-платформа под разными
   марками, а не запись сертификата нашего прибора. Собственный сертификат MIUC/0x0945 не
   найден. Отсюда «Matter 1.0» — указание, а не факт.
5. **Лимит фабрик в прошивке шлюза.** Спека требует ≥5; фактическое значение неизвестно,
   занято 3 (одна мертва). Публичных измерений `SupportedFabrics`/`CommissionedFabrics` ни
   для одного Tuya/MOES/AVATTO/Zemismart шлюза не существует; по веб-данным Apple Home
   занимает **два** слота. Прочитать атрибут можно только изнутри фабрики.
6. **Нужен ли мосту интернет — НИКЕМ не проверено.** Ни одного опубликованного теста
   Tuya-Matter-моста с обрезанным WAN не найдено. Все утверждения «это полностью локально» —
   маркетинг, уровень спеки или непроверенные форумные реплики; формулировка самой Tuya
   условная: «**With local control permissions**, the SDK allows your devices to run on a LAN
   when they are disconnected from the cloud». Смежный факт со стороны HA: у пользователя
